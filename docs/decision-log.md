# Decision Log

## ADR-001. Использовать redaction как основной механизм удаления

### Status

Accepted

### Решение

Сообщения старше 24 часов удаляются через Matrix `m.room.redaction`, а не через прямые SQL-операции и не через media cleanup.

### Причина

- redaction — штатный клиентский и федеративный механизм;
- он скрывает содержимое сообщения у клиентов;
- он не ломает внутреннюю модель хранения `Synapse`.

## ADR-002. Использовать Synapse DB только в read-only режиме

### Status

Accepted

### Решение

`Synapse DB` используется только для отбора кандидатов и анализа room state.

### Причина

- прямое изменение таблиц `Synapse` слишком рискованно;
- HTTP API остаётся единственной write-side точкой.

## ADR-003. Взять SQLAlchemy Core как единый DB abstraction layer

### Status

Accepted

### Решение

Все запросы к `Synapse DB` реализуются через SQLAlchemy Core.

### Причина

- нужен путь к PostgreSQL без переписывания логики;
- проект ориентирован на query layer, а не на heavy ORM.

## ADR-004. В strict режиме использовать сервисного Matrix-пользователя

### Status

Accepted

### Решение

Для строгого federated-режима приложение работает от имени отдельного сервисного пользователя, состоящего в комнатах и обладающего room-level правом redaction.

### Причина

- это единственный надёжный способ redaction'ить чужие события в federated rooms;
- admin API недостаточен как универсальный механизм “для всех пользователей во всех чатах”.

## ADR-005. Не использовать `retention` как базовый механизм проекта

### Status

Accepted

### Решение

`retention` и `m.room.retention` не выбираются как основной runtime-механизм.

### Причина

- проекту нужна управляемая адресная обработка конкретных `event_id`;
- нужен dry-run и поштучный отчёт по ошибкам;
- redaction лучше согласуется с operational control.

## ADR-006. Scheduler должен жить внутри контейнера

### Status

Accepted

### Решение

Расписание реализуется внутри контейнера через `supercronic`, а не через host cron.

### Причина

- это соответствует требованию запуска “внутри docker контейнера через docker-compose”;
- один и тот же образ можно переносить между серверами без внешнего планировщика.

## ADR-007. Суточный запуск в 05:00 трактуется как daily sweep

### Status

Accepted

### Решение

Расписание `0 5 * * *` документируется как ежедневный sweep, а не как точный TTL 24h.

### Причина

- при запуске раз в сутки невозможно получить точность “ровно через 24 часа” для каждого сообщения.

## ADR-008. Использовать allowlist event type

### Status

Accepted

### Решение

В первом релизе кандидатами считаются только типы:

- `m.room.encrypted`
- `m.room.message`
- `m.reaction`

### Причина

- это безопаснее, чем redaction всех non-state events;
- на текущем сервере это покрывает практически весь пользовательский трафик.

## ADR-009. Отдельно хранить локальный run journal приложения

### Status

Accepted

### Решение

Журнал запусков хранится отдельно от `Synapse DB`.

### Причина

- нужно фиксировать dry-run, real-run, ошибки и статистику;
- write-side следов в `Synapse DB` оставлять нельзя.

## ADR-010. Отвергнуть прямое удаление через `purge_history`

### Status

Rejected as primary mechanism

### Причина

- это грубая операция по истории комнаты;
- она не даёт удобного поштучного контроля над `event_id`;
- operationally хуже подходит под задачу регулярного селективного удаления.
