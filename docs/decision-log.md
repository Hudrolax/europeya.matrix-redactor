# Decision Log

## ADR-001. Использовать redaction как основной механизм удаления

### Status

Accepted

### Решение

Сообщения старше TTL удаляются через Matrix `m.room.redaction`, а не через прямые SQL-операции.

## ADR-002. Использовать `Synapse DB` только в read-only режиме

### Status

Accepted

### Решение

`Synapse DB` используется только для поиска кандидатов и preflight-проверок.

## ADR-003. Оставить SQLAlchemy Core как единый query layer

### Status

Accepted

### Решение

Все запросы к `Synapse DB` реализуются через SQLAlchemy Core.

## ADR-004. Работать только с локальными пользователями

### Status

Accepted

### Решение

Текущая архитектура поддерживает только локальных отправителей, потому что только для них приложение может опираться на данные локальной `Synapse DB`.

## ADR-005. Использовать существующие access token из `Synapse DB`

### Status

Accepted

### Решение

Для redaction используются уже существующие токены пользователей из таблиц `Synapse`.

## ADR-006. Не redaction'ить событие, если пользователь уже не состоит в комнате

### Status

Accepted

### Решение

Перед HTTP-вызовом приложение проверяет текущий membership пользователя в комнате и пропускает событие при отсутствии `join`.

## ADR-007. Scheduler должен жить внутри контейнера

### Status

Accepted

### Решение

Расписание реализуется внутри контейнера через `supercronic`, а не через внешнюю host-specific automation.

## ADR-008. Суточный запуск трактуется как daily sweep

### Status

Accepted

### Решение

Расписание раз в сутки документируется как sweep по условию “старше TTL”, а не как точный момент удаления.

## ADR-009. Использовать allowlist типов событий

### Status

Accepted

### Решение

Первый релиз ограничивает кандидатов конфигурируемым allowlist, а не всеми non-state событиями.

## ADR-010. Хранить run journal отдельно от `Synapse DB`

### Status

Accepted

### Решение

Локальная state DB приложения используется для истории запусков, skipped и failed событий.
