# Доступ к комнатам и права

## 1. Главный организационно-технический факт

Чтобы надёжно redaction'ить сообщения всех пользователей во всех комнатах, одного доступа к БД недостаточно.

Нужен исполнитель, который реально имеет право выпустить `m.room.redaction` в этой комнате.

Для строгого режима это означает:

- отдельный сервисный Matrix-пользователь;
- этот пользователь должен состоять в комнате;
- этот пользователь должен иметь достаточный `power level` для redaction чужих событий.

## 2. Почему это обязательно

### Для локальных пользователей

Synapse Admin API умеет redaction'ить события локального пользователя, но это не решает весь кейс “все пользователи во всех чатах”.

### Для federated пользователей

Если сообщение отправил пользователь с другого homeserver, то надёжное адресное redaction конкретного `event_id` требует штатного room-level права на redaction.

Именно поэтому strict mode строится вокруг сервисного пользователя в комнате.

## 3. Какой сервисный пользователь нужен

Рекомендуемый отдельный аккаунт:

- `@redactor:matrix.e1capital.ru`

Требования:

- локальный пользователь вашего homeserver;
- долгоживущий access token;
- не используется людьми;
- входит во все обслуживаемые комнаты.

## 4. Минимальные права в комнате

В каждой комнате сервисный пользователь должен:

- быть `join`;
- иметь право redaction чужих событий.

Практически это означает:

- его `power level` должен быть не ниже room `redact` threshold.

## 5. Что это означает для DM и приватных комнат

Это важное следствие архитектуры.

Если нужен strict mode даже для DM:

- сервисный пользователь должен быть добавлен и в DM;
- технически такая комната перестаёт быть чисто двухсторонней;
- это надо принять организационно.

Если это неприемлемо:

- строгая гарантия удаления всех сообщений во всех чатах невозможна;
- тогда придётся снижать требования или использовать local-only fallback.

## 6. Рекомендуемый preflight check

Перед первым боевым запуском приложение или отдельный admin runbook должны уметь проверить:

- сервисный пользователь состоит в комнате;
- комната существует;
- право redaction доступно;
- токен сервисного пользователя валиден;
- `Synapse` отвечает на Client API.

## 7. Что делать с существующими комнатами

Для уже существующих комнат нужна миграция доступа.

Практический порядок:

1. Создать сервисного пользователя.
2. Получить его access token.
3. Добавить его в комнаты.
4. Выдать ему нужный `power level`.
5. Прогнать dry-run.
6. Только потом включать real-run.

## 8. Что делать с новыми комнатами

Нужен процесс, который гарантирует присутствие сервисного пользователя во всех новых комнатах.

Это может быть:

- административное правило для пользователей;
- provisioning bot/process;
- отдельный серверный workflow за рамками данного приложения.

Без этого гарантия “во всех чатах” со временем будет деградировать.

## 9. Local-only fallback

Этот режим документируется только как ограниченная альтернатива.

Когда он допустим:

- если нужно redaction'ить только локальных пользователей;
- если федерация не критична;
- если добавление сервисного пользователя в комнаты организационно невозможно.

Когда он не подходит:

- если требуется строгая обработка federated users;
- если нужно жёсткое правило “все сообщения всех пользователей”.

## 10. Риски прав доступа

Если сервисный пользователь:

- не в комнате;
- kicked/banned;
- потерял `power level`;
- использует протухший token;

то приложение:

- не должно silently skip проблему;
- должно пометить комнату как failed;
- должно выдать отчёт, что policy для этой комнаты сейчас не исполняется.

## 11. Как это влияет на проект кода

В коде нужен отдельный слой `RoomAccessVerifier`, который:

- не просто пытается отправить redaction вслепую;
- а сначала умеет оценивать готовность комнаты.

Результат проверки должен попадать в run journal.

## 12. Вывод

Требование “удалять все сообщения старше 24 часов во всех чатах, включая федерацию” в Matrix упирается не в SQL, а в room permissions.

Поэтому сервисный пользователь с room-level redaction rights является обязательной частью целевой архитектуры, а не дополнительной опцией.
