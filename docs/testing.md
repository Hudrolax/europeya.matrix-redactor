# Тестирование

## 1. Цель тестирования

Нужно доказать, что приложение:

- правильно находит кандидатов старше TTL;
- не трогает события младше порога;
- не redaction'ит уже обработанные события;
- исключает комнаты из `ROOM_ID_EXCLUDELIST`;
- не делает HTTP-запросы для unsupported кандидатов;
- корректно выполняет redaction через Matrix API;
- безопасно ведёт себя при повторных запусках.

## 2. Уровни тестирования

### Unit tests

Проверяют:

- парсинг конфига;
- вычисление cutoff;
- retry policy;
- lock-поведение;
- классификацию skipped и failed результатов.

### Repository tests

Проверяют:

- SQLAlchemy-запросы на анонимизированной SQLite fixture;
- фильтрацию `state events`;
- исключение уже redaction'енных событий;
- исключение комнат из `ROOM_ID_EXCLUDELIST`;
- token lookup;
- current membership lookup.

### HTTP client tests

Проверяют:

- URL redaction endpoint;
- заголовок `Authorization`;
- поведение на `403`, `429`, `5xx`;
- retryable/permanent mapping.

### Integration tests

Проверяют end-to-end сценарий:

- выборка кандидата;
- preflight sender scope;
- preflight membership;
- запись run journal;
- отправка redaction для допустимых событий.

## 3. Dry-run

Dry-run должен показывать как минимум:

- общий count кандидатов;
- count по типам событий;
- count по комнатам;
- count по отправителям;
- sender scope summary;
- sample первых `N` кандидатов.

Dry-run не должен выполнять write-side действия.

## 4. Основные сценарии

### Сценарий A. Сообщение старше TTL

Ожидание:

- попадает в план;
- проходит preflight;
- в real-run получает redaction.

### Сценарий B. Сообщение младше TTL

Ожидание:

- не попадает в план;
- HTTP redaction не вызывается.

### Сценарий C. Уже redaction'енное событие

Ожидание:

- не попадает в план повторно.

### Сценарий D. Remote sender

Ожидание:

- событие маркируется как unsupported;
- HTTP redaction не вызывается.

### Сценарий E. Локальный пользователь без токена

Ожидание:

- событие пропускается;
- причина видна в отчёте.

### Сценарий F. Пользователь уже не состоит в комнате

Ожидание:

- событие пропускается до HTTP;
- приложение не ловит ожидаемый `403` на этом пути.

### Сценарий G. Retryable HTTP ошибка

Ожидание:

- `429` или временный сбой вызывают retry;
- после исчерпания retry ошибка фиксируется как failure.

### Сценарий H. Комната в `ROOM_ID_EXCLUDELIST`

Ожидание:

- события из комнаты не попадают в dry-run summary;
- события из комнаты не попадают в real-run batch;
- HTTP redaction не вызывается.

## 5. Smoke-test

Для ручной проверки достаточно изолированного окружения с тестовым `Synapse` или анонимизированной копией данных.

Минимальный порядок:

1. Подготовить несколько сообщений старше TTL.
2. Убедиться, что среди них есть как допустимые, так и skipped случаи.
3. Запустить `dry-run-report`.
4. Проверить summary.
5. Запустить `run-once --real-run`.
6. Проверить run journal и redaction events.

## 6. Негативные сценарии

Нужно отдельно проверять:

- недоступность `Synapse`;
- невалидный token;
- потерянный room membership;
- неверный mount SQLite каталога;
- overlap двух запусков;
- пустой или битый `.env`.

## 7. Тестовые данные

Требования к fixture-наборам:

- только обезличенные данные;
- никаких реальных access token;
- покрытие `m.room.encrypted`, `m.room.message`, `m.reaction`;
- отдельные кейсы для `join` и non-`join` membership.

## 8. Критерии готовности

Изменение можно считать принятым, если:

- unit и repository tests проходят;
- dry-run корректно отражает базовый кандидатный набор;
- комнаты из `ROOM_ID_EXCLUDELIST` не попадают в кандидатный набор;
- unsupported кандидаты не уходят в HTTP;
- retry policy работает предсказуемо;
- повторный запуск остаётся идемпотентным.
