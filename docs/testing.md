# Тестирование

## 1. Цель тестирования

Нужно доказать четыре вещи:

- приложение правильно находит кандидатов старше 24 часов;
- приложение не трогает события младше порога;
- приложение корректно redaction'ит сообщения через Matrix API;
- повторный запуск идемпотентен.

## 2. Уровни тестирования

### Unit tests

Проверяют:

- парсинг конфига;
- вычисление cutoff;
- нормализацию allowlist;
- генерацию `txnId`;
- классификацию ошибок;
- поведение lock manager.

### Repository tests

Проверяют:

- SQLAlchemy-запросы на копии SQLite БД;
- корректное исключение `state events`;
- корректное исключение уже redacted событий;
- батчинг;
- одинаковую семантику для SQLite и PostgreSQL dialect layer.

### HTTP client tests

Проверяют:

- корректный URL redaction endpoint;
- заголовок `Authorization`;
- retry policy;
- обработку `403`, `404`, `429`, `5xx`.

### Integration tests

Проверяют end-to-end сценарий:

- выборка события;
- отправка redaction;
- запись run journal;
- повторный запуск ничего лишнего не redaction'ит.

## 3. Обязательный dry-run режим

Прежде чем делать real-run, dry-run должен показывать:

- общий count кандидатов;
- count по типам событий;
- count по комнатам;
- список комнат, где нет нужных прав;
- список первых N кандидатов для ручной валидации.

Dry-run — это обязательная часть acceptance, а не “полезная опция”.

## 4. Набор основных сценариев

### Сценарий A. Сообщение старше 24h

Ожидание:

- попадает в план;
- в real-run получает redaction;
- исчезает у клиентов как message content.

### Сценарий B. Сообщение моложе 24h

Ожидание:

- не попадает в план;
- redaction не отправляется.

### Сценарий C. Уже redacted событие

Ожидание:

- не попадает в план повторно;
- повторный запуск не создаёт дубль.

### Сценарий D. Комната без прав

Ожидание:

- dry-run маркирует комнату как unsupported;
- real-run не уходит в бесконечные retries;
- итоговый отчёт содержит проблему явно.

### Сценарий E. Federated room

Ожидание:

- при наличии сервисного пользователя и `power level` redaction проходит;
- сообщение исчезает и у клиентов с другой стороны федерации.

## 5. Ручной smoke-test на боевом сервере

Рекомендуемый порядок:

1. Создать тестовую комнату с локальными пользователями.
2. Добавить сервисного пользователя.
3. Дать ему право redaction.
4. Отправить несколько тестовых сообщений.
5. Искусственно выбрать сообщения старше порога на staging-копии БД или временно использовать маленький TTL.
6. Запустить `run-once --dry-run`.
7. Проверить список кандидатов.
8. Запустить `run-once` в реальном режиме.
9. Проверить в клиенте, что сообщения стали redacted.

## 6. Ручной federated test

Отдельно нужен сценарий с federated room.

Порядок:

1. Взять room с локальным и внешним пользователем.
2. Убедиться, что сервисный пользователь в ней присутствует.
3. Дать ему room-level право redaction.
4. Отправить тестовые сообщения с обеих сторон.
5. Прогнать dry-run.
6. Прогнать real-run.
7. Проверить оба клиента.

## 7. Негативные сценарии

Нужно обязательно проверить:

- `Synapse` временно недоступен;
- token невалиден;
- room membership потерян;
- room power level недостаточен;
- DB path смонтирован неверно;
- SQLite sidecar-файлы недоступны;
- два запуска стартуют одновременно.

## 8. Тестовые данные

Для repository tests нужен отдельный fixture-набор:

- копия минимальной SQLite БД с несколькими событиями;
- отдельные случаи для `m.room.encrypted`, `m.room.message`, `m.reaction`;
- хотя бы одно уже redacted событие;
- одна комната с недостаточным доступом.

Важно:

- фикстуры должны быть обезличены;
- в тесты не должны попадать реальные access token пользователей.

## 9. Критерии готовности к production

Будущий релиз можно считать готовым только если выполнены все пункты:

- dry-run считает корректные цифры;
- real-run redaction'ит только ожидаемые события;
- повторный запуск идемпотентен;
- problems по комнатам видны в журнале;
- есть успешный federated test;
- есть успешный rollback plan на случай отключения сервиса.

## 10. Что считать rollback

В данном проекте rollback означает не “вернуть сообщения”, потому что redaction необратим.

Rollback здесь — это:

- остановить scheduler;
- отключить real-run;
- перевести сервис в dry-run;
- убрать доступы сервисного пользователя, если нужно.

Поэтому dry-run и staging-проверка обязательны до production включения.
